# 서울대 연구장비 구매문서 작성

## 무엇을 만드는가

| 산출물 | 양식 | 특징 |
|---|---|---|
| 구매규격서 | `assets/form3.hwpx` (별지 제3호) | 모델명 기재 불가. 공정 경쟁이 가능한 성능 규격으로 서술 |
| 용도설명서 | `assets/form2.hwpx` (별지 제2호) | 모델명 기재 가능. 실제 사양을 구체적으로 서술 |
| 검증 보고서 | 직접 작성하는 HTML | 위 두 문서가 목적에 맞는지, 규격이 방어 가능한지 대조한 기록 |
| (선택) 심의요청서 | `assets/form_review.hwpx` (표준지침 별표 4) | 자체연구시설장비심의위원회 제출용. 과제 부합성, 중복성, 활용성, 적정성, 계획성 서술 |
| (선택) 붙임 검토표 | `assets/form_review_attachment.hwpx` | ZEUS 조사 결과로 교내 유사장비를 대조한 중복성 검토표 |

두 문서는 짝이다. 규격서는 "이런 성능이 필요하다", 용도설명서는 "그래서 이 모델을 산다"를 말한다.

**심의요청서와 붙임은 선택 산출물이다.** 연구시설장비 심의(보통 3천만 원 이상 장비, 기관 규정에 따름)가
필요한 구매도 있고 아닌 것도 있으니, **작업을 시작할 때 사용자에게 필요 여부를 묻고** 필요하다고 하면
아래 「선택 산출물」 절을 따른다. 묻지 않고 만들거나, 묻지 않고 빼먹지 않는다.

## 도구

문서 편집은 **kordoc MCP**가 한다. HWPX의 XML을 직접 건드리지 않는다.

| 단계 | 도구 |
|---|---|
| 슬롯 수 맞추기 | `scripts/prepare_template.py` (규격서·용도설명서), `scripts/prepare_review.py` (심의요청서·붙임). 이 둘만 lxml을 쓴다 |
| 양식 읽기 | kordoc `parse_document` |
| 내용 채우기 | kordoc `patch_document` |
| 눈으로 검증 | `scripts/render_preview.py` (rhwp) |
| 유사장비 조사 | 내장 브라우저로 ZEUS(www.zeus.go.kr) 통합검색 (선택 산출물에서만) |

준비물: `pip install --user lxml rhwp-python`

### kordoc patch_document의 제약 — 반드시 숙지할 것

`patch_document`는 원본 서식을 1바이트도 건드리지 않고 텍스트만 제자리 치환한다. 대신:

1. **블록(문단) 수를 바꿀 수 없다.** 마크다운에 줄을 추가하면
   `블록 추가는 미지원 (v1)`으로 거절되고, 게다가 diff 정렬이 어긋나 **엉뚱한 문단까지 잘못 채워진다.**
   편집한 마크다운의 블록 수와 순서는 `parse_document` 출력과 정확히 같아야 한다.
2. **셀 안에서도 줄을 못 늘린다.** 늘리면 `셀 내 줄 추가는 문단 생성 미지원`이 뜨고 마지막 문단에 뭉쳐 들어간다.
3. **양식의 빈 문단은 파싱 때 사라진다.** 그래서 `patch_document`가 볼 수 없고 채울 수도 없다.

### 표가 쪽 경계에서 나뉘게 하기

**두 가지를 모두 손봐야 한다. 하나만으로는 안 된다.**

#### (1) "글자처럼 취급" 해제 — `hp:pos/@treatAsChar = "0"`

이것이 핵심이다. 글자처럼 취급된 개체는 한 글자와 동일하게 다뤄지므로 한글이 쪼개지 않는다.
표가 쪽에 안 들어가면 통째로 밀리거나 **쪽 밖으로 넘쳐 잘린다.**
이 값이 `1`이면 `pageBreak`를 무엇으로 두든 아무 효과가 없다.

배포 양식 중 별지 제3호는 `0`(자리 차지)이라 정상 동작하고, **별지 제2호만 `1`로 되어 있다.**
같은 서울대 양식인데 값이 다르다. 넘침이 보이면 여기부터 확인할 것.

#### (2) 쪽 경계에서 "나눔" — `hp:tbl/@pageBreak = "TABLE"`

| 값 | 한글 UI | 동작 |
|---|---|---|
| `NONE` | 나누지 않음 | 표가 한 쪽에 안 들어가면 통째로 다음 쪽으로 밀린다 |
| `CELL` | 셀 단위로 나눔 | 셀 경계에서만 끊는다. 셀 하나가 한 쪽보다 크면 소용없다 |
| `TABLE` | 나눔 | 셀 하나의 내용도 쪽 경계에서 갈라져 이어진다 |

이름과 달리 `TABLE`이 가장 잘게 나누는 값이다. 별지 제2호는 문서 전체가 표 하나이고
규격 셀 하나에만 20여 개 문단이 들어가므로 `CELL`로는 부족하다.

`prepare_template.py`의 `make_table_splittable`이 두 가지를 함께 처리하고,
표 안 문단의 조판 캐시(`hp:linesegarray`)도 지운다. 캐시를 남기면 한글이 예전 줄 배치를 재사용한다.

#### 확인 방법

`render_preview.py`가 rhwp의 조판 경고를 그대로 출력한다. 이 경고가 결정적 단서다.

```
!! 조판 경고 — 내용이 쪽 밖으로 넘쳤다는 뜻이다. 무시하지 말 것.
   LAYOUT_OVERFLOW: page=1, type=Table, y=1222.0, bottom=1035.6, overflow=186.4px
```

경고가 뜨면 표가 쪽 밖으로 넘쳐 **내용이 보이지 않는 상태**다. 페이지 수만 보면 놓친다.
실제로 넘치는 문서가 "1쪽"으로 렌더되어 정상처럼 보였고, 고친 뒤에는 2쪽에 걸쳐
잉크 행수가 360에서 966으로 늘었다. 3분의 2가 사라지고 있었던 것이다.

속성값 확인:

```bash
python3 -c "
import zipfile,sys; from lxml import etree
HP='{http://www.hancom.co.kr/hwpml/2011/paragraph}'
r=etree.fromstring(zipfile.ZipFile(sys.argv[1]).read('Contents/section0.xml'))
for t in r.iter(f'{HP}tbl'):
    print('pageBreak=',t.get('pageBreak'),'treatAsChar=',t.find(f'{HP}pos').get('treatAsChar'))
" 문서.hwpx
```

### 렌더링

kordoc `render_document`는 이 두 양식에서 실패한다(`렌더 실패: 문서 처리 중 오류`). `render_preview.py`를 쓸 것.
rhwp import가 `undefined symbol: FT_Palette_*`로 실패하는 환경이 있는데, 스크립트가 알아서 처리한다.

rhwp(0.8.x)의 한계 두 가지는 알고 보아야 한다.

- **셀 하나가 쪽을 넘기면 rhwp는 그 셀을 쪽 경계에서 나누지 못한다.** 문단을 한 개씩 새 쪽으로 밀어내다가
  나머지가 한 쪽에 들어가는 순간 전부 그 쪽에 넣는다. 그래서 별지 제2호처럼 규격 셀이 길면 미리보기에
  거의 빈 쪽이 2~3장 끼어 6쪽으로 나온다. 표 속성(`treatAsChar=0`, `pageBreak=TABLE`)이 정상이고
  경고가 없으면 한글에서는 셀이 이어져 조판되므로 렌더러의 문제로 보고, 최종 확인은 한글에서 한다.
- `LAYOUT_OVERFLOW ... type=PartialTable ... overflow=11px` 처럼 **표가 행 경계에서 나뉘는 자리의 10px 안팎 넘침**은
  rhwp가 스크립트의 경고 수집 밖으로 직접 찍는 메시지로, 행 경계의 테두리 선 두께 수준이다. 수십~수백 px이면 진짜 넘침이다.

## 작업 순서

### Step 1. 조사 (문서를 건드리기 전에 끝낼 것)

#### 1-1. 타겟 제품 사양

제조사 공식 스펙시트에서 수치를 빠짐없이 모은다. 최소 7~10개 카테고리, 카테고리당 2~5개 세부 항목.
공통으로 볼 것: 폼팩터와 치수, 전원, 동작 환경, 인터페이스, 관리 기능, 인증, 확장성.
장비 유형별로 더 봐야 할 항목은 `references/equipment_categories.md` 참조.

#### 1-2. 경쟁 제품 최소 3개

같은 세그먼트 제품을 3개 이상 찾아 사양을 비교하고, 다음을 정리한다.

- 타겟만 만족하는 항목 (규격서의 차별화 축)
- 모두 만족하는 항목 (써도 되지만 변별력 없음)
- 경쟁 제품만 만족하는 항목 (피할 것)

각 경쟁 제품이 2~3개 조건에서 걸리도록 조합을 설계한다. 한 항목으로 몰아서 떨어뜨리지 않는다.

#### 1-3. 관세분류번호(HSK)

`XXXX.XX.XXXX` 10자리. 관세법령정보포털(unipass.customs.go.kr) 또는 HS 속견표로 확인한다.
`references/equipment_categories.md`의 표는 출발점일 뿐이니 반드시 검색으로 확인할 것.

#### 1-4. 정부물품분류번호

조달청 물품목록(나라장터 goods.g2b.go.kr) 기준 **8자리까지만**. 세부품목으로 내려가지 않는다.
UNSPSC와 체계가 같으므로 UNSPSC 코드표로 교차 확인하면 빠르다.

### Step 2. 내용 작성

분량 기준은 아래와 같다. 슬롯 수를 정해야 Step 3을 돌릴 수 있으니 여기서 항목 수를 확정한다.

| 항목 | 최소 분량 |
|---|---|
| 용도 (규격서 Ⅰ) | 400자 이상, 한 문단. 앞 2/3는 장비 종류의 일반적 용도, 뒤 1~2문장만 연구실 용도 |
| 장비의 구성 (규격서 Ⅱ) | 본체 1줄 + 부속품 필요한 만큼 |
| 성능 및 규격 (규격서 Ⅲ) | 8~12개 항목, 각 항목이 해당 카테고리의 요구사항을 모두 담을 것 |
| 기타 조건 (규격서 Ⅳ) | 5~7개 항목 |
| 일반사양 (용도설명서 Ⅰ) | 8줄 이상 |
| 성능 (용도설명서 Ⅱ) | 6줄 이상 |
| 사용 용도설명 (용도설명서 5) | 3단락 이상, 각 2~3문장 |

핵심 원칙 세 가지만 여기 적는다. 자세한 작성법은 `references/spec_writing_guide.md`.

**상위 규격 장비는 반드시 통과시킨다.** 이것이 규격 작성의 제1원칙이다.
어떤 항목이 대상 모델보다 **우수한** 제품을 떨어뜨린다면, 그 항목은 필요를 적은 것이 아니라
대상 모델을 적은 것이다. 그 자체가 특혜 규격의 증거가 된다.

작성한 모든 수치 항목을 이 질문으로 검산한다. "이 제품보다 좋은 물건이 이 줄에서 걸리는가?"

- 클수록 좋은 값(코어 수, 용량, 포트 수, 대역폭, 인증 등급, 베이 수)은 **"이상"**으로만 쓴다.
- 작을수록 좋은 값(소비 전력, 소음, 오차, 차지하는 U 수, 깊이)은 **"이하" 또는 "이내"**로 쓴다.
  4U 장비를 살 때 "4U"라고 쓰면 더 조밀한 2U 60베이 제품이 걸린다. "4U 이하"로 써야 한다.
- 특정 규격을 지목할 때는 상위 호환을 열어 둔다. "IPMI 지원"은 Redfish만 지원하는
  더 나은 관리 체계를 배제하므로 "IPMI, Redfish 또는 동등 이상"으로 쓴다.
- 치수, 개수, 부품명으로 거는 항목은 대부분 이 검산을 통과하지 못한다. 성능 요건으로 바꾼다.
  "120mm 팬 6개 이상"이 아니라 "팬 1개 고장 시에도 만재 상태에서 규정 온도를 유지할 것".
- 범위를 쓸 때는 필요한 쪽 끝만 건다. 전산실에 둘 장비에 "0~35°C"를 요구하면
  5°C부터인 우수한 제품이 실익 없이 걸린다. "상한 35°C 이상"이면 충분하다.

**상한을 걸어도 되는 유일한 경우는 실제 물리 제약이다.** 보유 랙의 가용 깊이, 분전반 용량,
출입문 폭, 바닥 하중 같은 것이다. 이것들은 상위 제품이라서 걸리는 것이 아니라 들어가지 않아서
걸리는 것이므로 정당하다. 다만 Ⅲ. 성능 및 규격이 아니라 **Ⅳ. 기타 조건에 설치 요건으로** 적는다.

**규격서는 모델을 지목하지 않는다.** 브랜드명, 모델명, 독점기술명은 쓸 수 없다.
수치는 타겟 모델 실제값의 90~100% 수준에서 "이상 / 이하 / 이내 / 지원"으로 쓴다.
성능과 무관한 물리 치수나 내부 설계로 거르지 않는다. 다만 실제 설치 제약(랙 깊이 등)은
Ⅳ. 기타 조건에 설치 요건으로 적으면 정당하다.

**구매 주체는 "연구실"이 아니라 "과제"다.** 이것이 용도란에서 가장 흔하고 가장 위험한 실수다.
연구실을 주어로 쓰면("본 연구실은 ~를 수행하고 있으며") 그 연구실이 여러 과제에 두루 쓸
범용 장비를 과제비로 사는 것처럼 읽혀, 목적 외 사용으로 문제가 될 수 있다. 수요의 주체는
해당 과제이고, 장비는 그 과제의 목표를 달성하는 데 필요해서 사는 것이다.

| 쓰지 말 것 | 쓸 것 |
|---|---|
| 본 연구실은 ~를 상시 수행하고 있으며 | 본 과제는 ~를 규명하는 것을 목표로 하며 |
| 연구실 보유 서버 / 연구실 보유 랙 | 본 과제에서 운용 중인 서버 / 과제 수행 장소의 랙 |
| 연구실의 데이터가 증가하여 | 과제 수행 과정에서 데이터가 축적되어 |
| 연구원 대상 교육 | 과제 참여연구원 대상 교육 |
| 향후 다양한 연구에 활용 | (쓰지 말 것 — 목적 외 사용으로 읽힌다) |

**과제명은 본문에 쓰지 않는다.** 이 서류 자체가 해당 과제의 구매 절차에 첨부되므로
과제명은 이미 다른 서류에 적혀 있다. 본문에서는 "본 과제"로만 지칭한다. 다만 어느 과제인지는
사용자에게 물어야 한다. 과제마다 연구 목표와 필요성의 논리가 달라서 용도 서술이 바뀌기 때문이다.
알아낸 과제명은 서술의 방향을 잡는 데만 쓰고 문장에는 넣지 않는다.
장비의 활용 기간은 과제 기간에 걸어서 쓰고("과제 기간 전체에 걸쳐", "연차별 데이터 증가에 맞추어"),
증설이나 확장을 언급할 때도 과제 예산의 분산 집행으로 설명한다.
설치 장소만은 물리적 사실이므로 건물과 호실로 적되 "과제 수행 장소"로 표현한다.

**Ⅰ. 용도는 장비 종류의 일반적 용도를 먼저 쓴다.** 규격서를 읽는 사람은 구매 담당자와
심사자이지 그 분야 연구자가 아니다. 연구실 사정만 길게 늘어놓으면 읽는 사람은 이 장비가 무엇인지조차
알 수 없다. 이 종류의 장비가 무엇이고, 어떤 구조적 특징 때문에 어떤 일에 쓰이는지를 먼저 설명해야
Ⅲ의 성능 규격이 왜 그렇게 쓰였는지 납득이 된다. 연구실 고유의 용도는 맨 뒤에 1~2문장으로 덧붙인다.
분량은 일반적 용도가 3분의 2 이상이다. 반대로 용도설명서(별지 제2호)의 "5. 사용 용도설명"은
우리 용도를 자세히 쓰는 자리다. 두 문서의 역할을 섞지 말 것.

**용도설명서는 구체적으로 쓴다.** 모델명을 쓰고 실제 사양을 그대로 적는다.
연구 맥락에서 왜 이 사양이 필요한지가 드러나야 한다.

### Step 3. 슬롯 수 맞추기

```bash
python3 scripts/prepare_template.py --form 3 \
    --in assets/form3.hwpx --out work/구매규격서_작업본.hwpx \
    --specs 10 --remarks 6 --accessories 3

python3 scripts/prepare_template.py --form 2 \
    --in assets/form2.hwpx --out work/용도설명서_작업본.hwpx \

```

Step 2에서 정한 항목 수와 정확히 같게 준다. 나중에 바꾸려면 작업본부터 다시 만든다.

이 단계에서 함께 처리되는 것:

- 표의 `treatAsChar`를 0으로, `pageBreak`를 `TABLE`로, 조판 캐시 제거 (`make_table_splittable`)
- Ⅲ, Ⅳ의 작성 안내문 삭제 (`remove_guide_notes`) — kordoc이 문단을 못 지우므로 여기서 해야 한다
- 별지 제2호 빈칸에 자리표시자 삽입
- 별지 제2호 규격 셀·용도 셀의 문단 서식 통일 (`unify_cell_paragraph_style`) — 양식은 슬롯마다 줄간격이
  130%/160%/고정/230%로 달라 채우면 들쭉날쭉해진다. 'Ⅰ. 일반사양' 문단의 서식(160%)으로 맞춘다
- 양식 문구 탐색은 대소문자를 무시한다 (`2. Accessories`처럼 대문자로 시작하는 양식도 있다)

### Step 4. 채우기

1. kordoc `parse_document`로 **작업본**을 읽는다 (원본 양식이 아니다).
2. 출력 마크다운에서 텍스트만 바꾼다. 줄을 더하거나 빼지 않는다.
   - 맨 앞 `[포맷: HWPX | 페이지: 1]` 줄은 빼고 넘긴다.
   - 구매규격서: 표 데이터행 6칸, `Ⅰ. 용도` 안내문 1줄, 구성품, `1.`~`N.` 규격, `1.`~`M.` 기타조건.
   - 용도설명서: `GS01`, `PS01`, `UD01` 자리표시자를 전부 실제 내용으로 바꾼다. **하나라도 남으면 문서에 그대로 찍힌다.**
   - `Ⅰ. 용도`의 `- 어떤 업무에 사용되는 지 기술 -`은 **용도 본문이 들어갈 자리**이니 내용으로 덮어쓴다.
   - Ⅲ, Ⅳ의 안내문(`- 특정 모델명이나 ... 기재 -`, `- 설치조건, 보증조건, 훈련 조건, 납기 등 -`)은
     `prepare_template.py`가 이미 지웠으므로 파싱 결과에 나오지 않는다. 최종 문서에 이런 작성 지침이
     남아 있으면 안 된다.
3. kordoc `patch_document` 실행. `완전 일치`가 아니면 고쳐서 다시 한다.

### Step 5. 조판 검증

```bash
python3 scripts/render_preview.py work/구매규격서.hwpx --out work/preview/규격서
```

생성된 PNG를 **직접 열어서 눈으로 확인한다.** 파싱 결과만 믿지 않는다. 볼 것:

- 자리표시자(`GS01` 등)가 남아 있지 않은지
- 표 칸에서 글자가 잘리거나 글꼴이 줄어들지 않았는지
- 항목 번호가 연속하는지
- **조판 경고가 없는지** (경고 = 내용이 쪽 밖으로 사라진 상태)
- 페이지 수가 내용 분량과 맞는지 (분량이 많으면 용도설명서도 2쪽이 정상이다)

렌더링이 컨테이너 밖(사용자 컴퓨터)에서 돌면 PNG를 스테이징해서 볼 것.

PNG를 볼 수 없는 상황(스테이징 불가 등)이면 차선책으로 구조 점검이라도 한다.
kordoc의 이미지 OCR(parse_document)은 이 렌더 결과에서 실패하므로, 픽셀 통계를 쓴다.

```python
from PIL import Image; import numpy as np
im = np.asarray(Image.open('preview/용도설명서_p1.png').convert('L'))
ink = (im < 160)
rows = np.nonzero(ink.sum(axis=1) > 0)[0]
print('본문 끝 위치', round(100*rows[-1]/im.shape[0]), '%')   # 95% 넘으면 넘칠 위험
```

표 세로선을 피한 가운데 세로 영역(예: x 420~980)에서 줄간격을 재면 글꼴 축소도 잡힌다.
정상값은 scale 1.6 기준 줄간격 약 38px, 글자 높이 약 24px이다. 이보다 크게 작으면
글꼴이 줄어든 것이니 분량을 줄이거나 슬롯 수를 다시 잡는다.

### Step 6. 검증 보고서 (필수)

문서가 완성되면 **반드시** 아래 세 가지를 확인하고 self-contained HTML 보고서로 남긴다.
문서와 같은 폴더에 `검증보고서_<품명>.html`로 저장한다. 외부 CSS나 스크립트, 웹폰트를 참조하지 않는다.

#### 6-1. 목적 적합성

구매 목적의 각 요구가 실제 규격 항목으로 번역되었는지 한 줄씩 대조한다.
목적에 있는데 규격에 없는 것, 규격에 있는데 목적으로 설명되지 않는 것을 모두 찾는다.
후자가 특히 위험하다. 근거 없는 규격은 특정 제품에 맞춘 것으로 읽힌다.

#### 6-2. 경쟁 제품 4종 이상 대조

**Step 1-2에서 조사한 3종으로는 부족하다. 검증 단계에서는 4종 이상을 쓴다.**
실제 조달 가능한 근접 제품을 고르고, 공개된 제조사 사양으로 규격 항목을 하나씩 판정한다.

- 충족 / 미충족 / **불명** 세 가지로 판정한다. 제조사가 공표하지 않은 항목을
  미충족으로 처리하면 안 된다. 그것은 검증이 아니라 희망이다.
- 제품마다 **배제 항목 수**를 센다. 1개 항목으로만 배제되는 제품이 있으면 그것이 취약점이다.
- 각 배제 근거가 "더 우수한 장비만 통과시키는" 논리인지 따진다. 성능이 아니라
  치수, 개수, 부품 지정으로 걸리는 항목은 `references/spec_writing_guide.md`가 금지하는
  유형이므로 성능 요건으로 바꿀 것을 권고한다.
- 배제 논리가 약해서 경쟁 제품이 규격을 충족하게 되더라도, 그 사실을 숨기지 말고 보고한다.
  적격 제품이 2종인 편이 단독 규격보다 조달 절차상 안전하다. 무리한 차별화가 더 위험하다.

#### 6-3. 분류번호 재확인

HSK와 정부물품분류번호를 근거와 함께 다시 확인하고, 확인하지 못한 부분을 명시한다.

- unipass와 나라장터는 자동 조회가 막히는 경우가 많다. 막혔으면 막혔다고 적고
  구매팀이나 관세사가 확인할 항목으로 넘긴다. 확인한 척하지 않는다.
- HSK는 **납품 형태에 따라 분류가 달라질 수 있다.** 예를 들어 디스크 인클로저는
  드라이브를 장착해 들여오면 기억장치(8471.70)지만 공(空) 섀시면 부분품(8473.30)으로 갈 여지가 있다.
  이런 갈림길을 보고서에 적어 둔다.

#### 보고서 구성

종합 판정 → 목적 적합성 → 경쟁 제품 대조표 → 배제 논리의 강도 → 분류번호 검증 → 조치 목록 → 출처.
종합 판정은 맨 위에 두고, 보완이 필요하면 무엇을 고쳐야 하는지 첫 문단에서 말한다.
표는 가로 스크롤이 되게 감싸고, `@media print`로 인쇄 시 표가 쪼개지지 않게 한다.
다크 모드는 `prefers-color-scheme`로 대응한다.

## 선택 산출물: 연구시설장비 심의요청서 + 붙임 유사장비 검토표

시작할 때 물어서 필요하다고 한 경우에만 만든다. 규격서·용도설명서(Step 1~6)를 먼저 끝내고 그 조사 결과를 재사용한다.
양식은 예시가 채워진 상태의 HWPX이므로, 채우기 전에 `prepare_review.py`로 문단·행 수를 맞추고 자리표시자를 넣는다.

### R1. 물어야 할 것

규격서에서는 과제명을 본문에 쓰지 않지만, 심의요청서에는 **과제명 칸이 있다.** 아래를 한 번에 묻는다.

| 항목 | 비고 |
|---|---|
| 과제명 | 그대로 기재. 서술의 주어도 "본 과제" |
| 구축 장소(건물·호실) | "추후 협의"가 안 된다. 설치예정 세부 장소 칸이 있다 |
| 분류5 활용목적 | 공동활용허용(Joint Use)이 기본. 단독활용이면 중복성 항목의 논리를 더 강하게 써야 한다 |
| 구축 일정 | 발주예정일·설치예정일 구간. 견적서 납기(예: 발주 후 10~12주)로 역산해 기본값을 제시 |
| 비교 견적 | 타 제작사 견적 PDF가 있으면 받는다. 없으면 ZEUS 동일 기종 취득가로 대신한다 |
| 교내 유사장비에 대해 이미 아는 것 | 사용자가 아는 "왜 못 쓰는지"(각도, 시료량, 거리, 소유·사용량)가 중복성 항목의 뼈대다 |

담당자 정보와 전문기술인력 행(성명, 학위, 고용형태, 담당장비수)은 예시 양식의 값을 그대로 두고 결과 보고에서 확인을 청한다.

### R2. ZEUS 유사장비 조사

내장 브라우저로 `https://www.zeus.go.kr/` 을 열고 상단 통합검색을 쓴다. 팝업은 무시하고 URL로 바로 간다.

```
https://www.zeus.go.kr/search?keyword=<검색어>&category=PRODUCT&subCategory=EQUIP
    &includeKwd=서울대학교&srchFd=all&orKwd=false&alwaysKwd=false&date=all&pageNum=1&preKwd=<검색어>
```

- `includeKwd=서울대학교`가 보유기관 필터 역할을 한다. 검색어는 모델 계열명(Zetasizer, Litesizer, ELSZ …)과
  일반명(제타전위, 입도분석, 동적광산란, 광산란 …)을 여러 개 돌려 합집합을 만든다.
- 목록에는 설치 건물이 없다. **상세 페이지** `/search/equip/read/<id>` 에 취득금액, 취득일자, 활용범위, 단독활용사유,
  표준분류, 연구책임자, 세부과제명, 위치(건물·호실), 사양 요약, "타기관 동일시설장비" 취득가가 있다.
- 페이지 안에서 `javascript_tool`로 `fetch()`를 돌리면 빠르다. 단, 검색·상세 URL에 **`&sso_status=N`을 붙여야**
  SSO 로그인 확인 페이지로 튕기지 않는다. 결과 HTML을 `DOMParser`로 파싱해 `a[href*="/search/equip/read/"]`와
  라벨(시설장비등록번호, 취득금액, 위치보기 …) 다음 줄을 뽑는다.
- 검색어마다 "총 N건"을 기록해 붙임의 검토 방법 줄에 적는다. 원리가 다른 장비(레이저 회절, NTA, MALS)는 표에서 뺀다.
- 사용자가 아는 장비가 ZEUS에 없으면(등록 대상 미만, 다른 이름 등록) "ZEUS 미등록·자체 확인" 표로 따로 적고 출처를 밝힌다.
- 상세 페이지의 "타기관 동일시설장비" 취득가 목록은 적정성 항목의 가격 비교 근거로 그대로 쓴다.

### R3. 내용 작성 원칙

예시 양식(자동분주장치)의 문장 구조를 따르되, **장비 성격에 맞는 논리 축을 고른다.** 예시는 "상시 관리 공정 장비"였고,
분석기기라면 보통 다음 넷이다. 각 축은 사용자가 준 사실(각도, 시료량, 거리, 소유·사용량)에서 나와야 한다.

1. 측정 시점의 제약 — 시료가 시간에 민감하면 예약제 공동장비로는 일정이 안 맞는다
2. 광학·측정 구성의 차이 — 기구축 장비가 필요한 측정 항목을 못 한다 (예: 90° 단일 각도, 제타전위 없음)
3. 시료량 규모의 차이 — 요구 시료량이 연구 규모와 안 맞는다 (예: 1 mL 셀 vs 50 µL 제형)
4. 이동 거리와 접근성 — 다른 캠퍼스, 개별 연구실 소유로 상시 출입이 비현실적

적정성 항목은 세 비교를 다 넣는다: 타 제작사 견적(있으면), ZEUS 동일 기종 취득가 범위와 교내 기구축가, 상위·하위 모델을
고르지 않은 이유. 신청가가 비교 견적보다 높으면 그 차이가 어느 요구를 충족하는 데서 오는지 항목별로 적는다.

분류표: 분류1 기술분야, 분류2 표준분류(ZEUS 상세의 "표준분류" 대·중·소분류를 그대로), 분류3 분석용/시험용,
분류4 중점투자분야, 분류5 활용목적. ○ 위치를 옮길 때 원래 ○가 있던 칸은 빈 문자열로 두면 kordoc이 지운다.

### R4. 문단·행 수 맞추기

```bash
python3 scripts/prepare_review.py --form request \
    --in assets/form_review.hwpx --out work/심의요청서_작업본.hwpx \
    --cell t2:r18c2=O--O--O- --cell t2:r21c2=O---O---O--O-O--O-- --cell t2:r22c2=O--O-- \
    --cell t3:r1c1=O---O--- --cell t3:r2c1=O-------O--O--O-O--O --cell t3:r3c1=O-----O--O--- \
    --cell t3:r4c1=O----O---O--O---O--O --cell t3:r8c1=O--O---O--O---

python3 scripts/prepare_review.py --form attachment \
    --in assets/form_review_attachment.hwpx --out work/붙임_작업본.hwpx \
    --body "□○--○----□○T1:18○------□○T2:3○○□○----○---○--○--○---※" \
    --tables work/붙임_표내용.json
```

- `O`는 '○ ' 항목 문단, `-`는 '- ' 세부 문단이다. 초안을 먼저 쓰고 각 칸의 패턴을 세어서 준다.
- 붙임의 `--body`는 본문 문단을 앞에서부터 한 글자씩 적은 것이고 `T1:18`은 1번 표를 데이터 18행으로 만든다.
- **붙임의 표는 kordoc이 채우지 못한다.** 맨 앞 제목 표 때문에 "표 개수 불일치"로 표 편집을 건너뛴다.
  그래서 표 내용은 `--tables` JSON(`{"1": {"header": [...], "rows": [[...]], "widths": [13.6, 11.9, 7.8, 7.3, 7.8]}}`)으로
  준비 단계에서 넣는다. `widths`는 열 너비 비율이다. 예시 양식의 2열('설치장소')은 좁아서 모델명을 넣으면 꺾이므로 꼭 다시 나눈다.
- 개요·목적 표는 `pageBreak=TABLE`, 데이터 표는 `CELL`(행 경계에서만 나눔)로 바뀐다.

### R5. 채우기와 검증

1. 작업본을 `parse_document`로 읽고 자리표시자(`T2R18C2-01`, `B01`)를 전부 실제 문장으로 바꿔 `patch_document`.
2. 붙임은 "검증 잔차: 수정 N"이 나올 수 있다. `~`가 `\~`로 재파싱되는 차이일 뿐이다. 출력물을 다시 `parse_document`해서
   본문이 의도대로 들어갔는지, 표가 그대로인지 확인한다. 자리표시자와 예시 문구(Opentrons, 자동분주 등)가 남았는지 XML 텍스트로 전수 검색한다.
3. `render_preview.py`로 렌더한다. 심의요청서는 셀마다 쪽이 나뉘어 7~8쪽으로 보이는데, 위 「렌더링」의 rhwp 한계 그대로이다.
4. 검증 보고서 HTML에 「심의요청서·붙임」 절을 추가한다: ZEUS 조회 건수와 조회일, 표에 넣은 장비 목록의 출처,
   ZEUS에 없어서 자체 확인으로 적은 장비, 예시 값을 그대로 둔 칸(담당자, 인력 행), 비교 견적 출처.

## 파일 구조

```
snu-procurement-doc/
├── SKILL.md
├── assets/
│   ├── form2.hwpx                    ← 용도설명서 원본 양식 (수정하지 말 것)
│   ├── form3.hwpx                    ← 구매규격서 원본 양식 (수정하지 말 것)
│   ├── form_review.hwpx              ← (선택) 심의요청서 양식, 예시 내용이 채워진 상태
│   └── form_review_attachment.hwpx   ← (선택) 붙임 유사장비 검토표 양식, 예시 내용이 채워진 상태
├── scripts/
│   ├── prepare_template.py     ← 규격서·용도설명서 슬롯 수 맞추기 (채우기 전에)
│   ├── prepare_review.py       ← 심의요청서·붙임 문단·행 수 맞추기, 붙임 표 채우기
│   └── render_preview.py       ← PNG 렌더 (채운 뒤에)
└── references/
    ├── spec_writing_guide.md   ← 공정 규격 작성법
    └── equipment_categories.md ← 장비 유형별 참고 정보
```

산출물은 구매규격서 HWPX, 용도설명서 HWPX, 검증 보고서 HTML 세 가지다. 세 개를 같이 낸다.
심의요청서를 만들기로 했으면 심의요청서 HWPX와 붙임 검토표 HWPX가 더해져 다섯 개가 된다.
